# Experimental methodology

## Scope

The modern implementation in this repository studies three algorithms over a
**deliberately reduced DES state space**:

1. exhaustive search;
2. Hellman time-memory tradeoff tables;
3. distinguished-point time-memory tradeoff tables.

DES is obsolete. These experiments are educational/reproducibility artifacts,
not a claim about the cost of attacking full DES and not production
cryptographic software.

The original Eclipse prototype and original presentation are preserved
separately as historical artifacts.

## Effective reduced key space

A DES key is represented by eight bytes, but one bit in each byte is a parity
bit. The modern model therefore counts **effective DES key bits**, not raw Java
byte-representation bits.

The first four DES bytes are fixed. The last four bytes contain at most seven
effective variable bits each, so the largest reduced state dimension supported
by the model is 28 bits.

For an experiment with `b` effective state bits,

\[
N = 2^b.
\]

Each integer state in `[0, N)` maps deterministically to one DES key encoding
with odd parity.

This corrects an ambiguity in the historical prototype, where four varying raw
DES bytes could be described informally as "32 bits" even though DES parity
means at most 28 of those bits affect the cipher key.

## Fixed plaintext and state transition

All modern benchmark methods use the same fixed plaintext fixture.

For state `x`, let `K(x)` be its encoded DES key, `E` DES encryption of the
fixed plaintext, and `R` the reduction function. A chain transition is

\[
x_{i+1}=R(E_{K(x_i)}(P)).
\]

The reduction follows the effective-bit structure of the historical prototype:
it reads the final four ciphertext bytes, removes the DES parity-bit position
from each byte, forms a 28-bit value, and masks it to the configured reduced
state dimension.

## Exhaustive search

States are tested in ascending integer order. Recovery is successful only when
the recovered reduced state is exactly the state used to construct the target
ciphertext.

Because the target state is sampled uniformly, exhaustive-search timing depends
on the sampled target position. The measurements are therefore useful as
end-to-end observations, not as stable microbenchmarks.

## Hellman tables

A Hellman table is generated from `m` distinct random start states. Every chain
uses exactly `t` transitions and stores its final endpoint.

Endpoint lookup uses a hash index. If multiple chains share an endpoint, all
candidate starts are retained and candidate chains are regenerated to verify
the target ciphertext.

If the `m t` visited states were independent uniform samples, the usual
occupancy reference would be

\[
1-\exp(-mt/N).
\]

The chain states here are **not independent samples**: each state is obtained by
iterating one fixed mapping. Chain merging therefore makes this occupancy value
optimistic. The curated benchmark separately computes exact unique-state table
coverage so the result does not rely on this approximation.

## Distinguished points

A reduced state is distinguished when its lowest `d` state bits are zero.
Under a uniform-state heuristic, the expected waiting time to a distinguished
point is approximately

\[
2^d
\]

transitions.

Each chain is bounded by a configurable maximum number of transitions. Chains
that do not reach a distinguished point before the cutoff are counted as
truncated and are not stored.

Chains sharing a distinguished endpoint are all retained. Online lookup
projects the target forward to a distinguished endpoint and regenerates stored
candidate chains. The implementation returns only the state whose encryption
is actually verified against the target ciphertext.

## Randomness and reproducibility

Experiment start states and target states are generated by Java
`SplittableRandom` from an explicit seed. Start states within one table are
unique.

The curated small benchmark uses an explicit seed and writes raw CSV rows to
`experiments/results/verified-small.csv`.

## Timing

Durations are measured with `System.nanoTime()`.

The benchmark script performs a small JVM/JCE warm-up run before collecting the
curated result set. The measured values remain ordinary end-to-end JVM timings;
they are **not JMH microbenchmarks**, cycle counts, or hardware throughput
measurements.

The environment used for a curated run is recorded in
`experiments/results/verified-small-environment.txt`.

## Interpretation

The most defensible outputs are:

- exact-recovery rate across seeded trials;
- table shape and endpoint-collision evidence;
- distinguished-chain truncation counts;
- end-to-end offline/online timings on the recorded machine.

Historical presentation numbers are kept separate in
`HISTORICAL_RESULTS.md`. They are not silently mixed with newly reproduced
measurements.
